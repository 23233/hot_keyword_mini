## 一、结论摘要

**技术上可以实现“一个 Go 后端承载两个小程序，并将客户端逐步切换到 SDUI”，但不能通过简单复制页面或直接替换接口完成。** 推荐把当前 `hot_keyword_mini` 作为统一控制面和 SDUI 基础设施，在其上只迁移第一个小程序的游戏业务，再为第二个小程序补齐独立的斗草斗粮业务域，最后分别发布客户端。

需要特别区分三件事：

1. **SDUI 负责页面协议、布局、受控动作和发布回滚。** 它不能凭空提供游戏同步、兑换库存、购物车、订单、物流、售后、斗师接单或客服线索等领域事务。
2. **第一个小程序只迁移游戏域，不迁移旧用户态。** 旧用户中心、旧 AES 通信、旧单 JWT、关注、评论、UGC、订阅消息、自动兑换、兑换记录、防屏蔽工具和个人中心均不在本次迁移范围内；页面匿名浏览，兑换码按需从受控端点获取并立即复制。首发可匿名请求，服务端仅保留库存扣减和幂等所需的最小技术记录，不提供用户可见兑换记录或历史入口。
3. **第二个项目目前是 H5 原型，不是已接通业务的小程序。** `dcl` 的 204 条路由已经有较完整的 UI、状态机和测试，但数据层明确使用 `H5MockApiClient`；它还没有可上线的真实业务后端。

因此，最终目标应定义为：

```text
一个统一 Go 后端
  ├─ 公共租户、鉴权、SDUI、发布、资源、审计能力
  ├─ 设身处地游戏业务域（不迁移旧用户态）
  └─ 斗艺馆业务域（先合规内容/服务，再交易和斗师工作台）

两个微信小程序客户端
  ├─ 第一个：已上线版本升级为通用 SDUI 运行时，通过配置承载设身处地游戏页面
  └─ 第二个：复用同一套 SDUI 运行时和协议，以 dcl H5 设计为页面来源

一个可选 H5 客户端
  └─ 保留 dcl 的 Web 运行时，但把 Mock 数据客户端替换为真实 HTTP 适配器
```

### 按“同一 SDUI 协议”重新评估

| 项目 | 统一 SDUI 运行时适配度 | 首发动态发布能力 | 主要限制 |
| --- | --- | --- | --- |
| 设身处地游戏 | 高 | 首页、游戏中心、游戏详情、兑换码、导航、游戏资料、已登记 WebView，以及预置能力包都可由后台启用或隐藏 | 首发只启用游戏能力；支付、上传、客服等能力需要在后端接入真实业务后再开启 |
| dcl / 斗艺馆小程序 | 中高，适合复用同一内核 | 内容、百科、品牌、斗师/作品展示、商品展示、页面路径、功能分支，以及预置交易/服务能力都可后台启用 | H5 Mock 还不是生产业务；订单、支付、物流、售后、斗师工作台、实时聊天必须完成真实领域服务、权限和审核材料后才能开启 |

这意味着两个小程序可以共用：

- 同一套 SDUI 信封、Schema、Block 注册表、Action 注册表和协议校验；
- 同一套 Taro/React 页面承载、缓存、ETag、错误处理、降级和安全回退；
- 同一套后台页面编辑、草稿、发布、回滚、页面显示/隐藏和能力矩阵校验；
- 同一套 WebView 容器，但每个 AppID 独立配置业务域名和允许的 `url_key`。

不能合并的是：

- 两个微信 AppID 的代码包、版本审核、隐私协议、类目和业务域名配置；
- 游戏域与斗艺馆域的领域数据、权限、订单/库存事务和内容合规规则；
- 每个小程序实际已经审核通过的能力封套。

所以“只完成一个小程序的认证审核”可以理解为：**客户端通用运行时和完整能力封套只设计、开发和维护一套；每个 AppID 在首次提交时按自身业务范围提交这套能力封套，之后通过 SDUI 动态启用已审核能力。** 不能理解为：一个 AppID 的审核结果自动覆盖另一个 AppID，或通过 SDUI 新增未审核业务而不再提交审核。

## 四、核心技术结论

### 4.1 不能把两个现有 Go 项目直接合并

第一个小程序的 `duihuanma_miniapp` 是一套真实业务后端；当前 `hot_keyword_mini` 是另一套 SDUI/资讯后端。它们存在同名但语义不同的表和模型，直接复制文件会造成不可控冲突：

- 两边都有 `users`，但目标用户已经有 `app_id`，源用户没有，且字段集合不同；
- 两边都有 `articles`，但源项目是游戏攻略文章，目标项目是带会员等级、试读、单篇购买和评论审核的 AI 文章；
- 目标项目有 `products`、`payment_orders`，源项目没有相同的商城订单语义；
- 源项目的 `share_templates` 是独立表，目标项目把分享配置放进 `DynamicPage`；
- 两边的管理员、JWT、响应信封、加密方式和错误码均不一致。

本次范围下，正确做法是：**以当前 SDUI 后端为统一骨架，只迁移源项目的游戏领域模型、服务和接口；不迁移源用户表、旧登录、旧加密和旧个人中心；数据表采用明确的迁移映射，不在同一个模型上强行兼容两种语义。**

### 4.2 SDUI 的正确边界

下列能力可以优先直接用现有 SDUI 表达：

- 设身处地游戏动态首页、游戏中心、游戏详情、游戏兑换码页；
- 斗艺馆首页、百科首页、品牌馆、斗型/材质知识、文章详情、斗师列表、作品详情、合规市集列表；
- 图片、文字、富文本、网格、列表、Tab、轮播、内容流、商品卡、表单、状态块、分享和登录拦截；
- 空态、错误态、加载态、过期、下架、未登录和客户端能力不足等页面状态。

下列能力可以继续使用通用积木，但必须先实现真实后端端点和事务：

- 兑换码请求、兑换结果复制、游戏资料读取和必要的库存幂等控制；
- 戳记/年份查询、估价、客服线索提交、斗师预约、库存监听；
- 收藏、购物车、订单创建、支付、订单状态、订阅消息。

下列能力不能仅靠现有 SDUI 配置完成，必须新增领域服务、数据模型、权限和可能的原生组件：

- 地址簿、物流轨迹、退款/售后、纠纷和订单状态机；这些属于第二个小程序，不属于第一个小程序本次迁移；
- 斗师入驻认证、接单工作台、报价、收件、回寄、结算；
- 多渠道身份映射、H5 邮箱/手机/OAuth 登录；
- H5 SEO、地区/年龄策略、跨区域商品可见性；
- 微信客服/企业微信/客服线索分配和运营报表。

这里的“需要新增”不等于每个页面都要新增一个专用组件。优先顺序应是：先用 `container`、`list`、`form`、`content_*`、`game_card`、`redeem_code_card`、`product_card` 等现有块组合；只有交互语义或原生能力确实无法表达时，再新增通用块或动作。

这里需要修正“不能仅靠 SDUI 配置完成”的含义：它不是说这些能力不纳入本轮开发，而是说不能只写页面 JSON。它们必须以统一能力包纳入本轮开发，页面 JSON 只负责组合和启用，不能负责实现支付、库存、消息、权限或资金安全。

每个能力包统一分为四层：

1. **SDUI 表达层**：Block 的字段、状态、事件、空态、错误态和降级表现；
2. **客户端适配层**：Action 白名单、微信原生 API、缓存、轮询/WebSocket、上传进度和失败恢复；
3. **后端领域层**：数据模型、权限、事务、幂等、状态机、回调、审计和错误码；
4. **运营控制层**：AppID/租户能力矩阵、页面显示/隐藏、入口开关、审核版本、域名白名单和发布门禁。

只有四层都存在，某项能力才算“已内置”；否则只能标记为视觉原型或协议占位，不能对外宣称后续可以直接启用。

### 4.3 当前 SDUI 代码需要做的通用化调整

当前 `services/sdui.go` 的 `assembleDomainEntity` 通过 `switch businessType` 直接写死短剧、游戏、查询和下载。迁移两个真实业务时，不建议继续堆叠 `case duihuanma`、`case douyiguan`。

建议做一个足够小的“业务适配器注册表”：

- 适配器负责按页面声明的数据源和查询参数装配非敏感实体；
- 受控动作端点负责事务、权限、幂等和敏感字段；
- `business_type` 只作为分类/归因标签，不决定客户端渲染分支；
- 页面协议继续只传 `entity`、`id`、`fields`、`filters`、`cursor`、`limit` 等受控参数；
- 禁止下发任意 SQL、脚本、Authorization、Cookie 或内部请求头。

这是一层简单的注册表，不需要引入动态插件系统或复杂规则引擎，符合 KISS 原则，同时避免后续每个行业都改动 SDUI 内核。

### 4.4 首页目标与页面显示/隐藏协议

首页不能只保存一个 `current_page` 字符串，否则无法表达“进入某个游戏详情”“进入某个游戏兑换码页”和“打开指定 H5”这三种目标。建议把首页目标抽象为受控对象，后台只允许选择已发布、未隐藏的页面或已登记的 WebView 地址：

```json
{
  "type": "page",
  "page_id": "game-detail",
  "params": {"game_id": "game-001"}
}
```

或：

```json
{
  "type": "webview",
  "url_key": "approved_game_home"
}
```

实现上可以保留 `MiniApp.CurrentPage` 作为旧字段，同时新增 `HomeTarget` JSON 字段；读取时优先使用 `HomeTarget`，没有新值时兼容旧的 `CurrentPage`。`url_key` 必须由服务端映射到 HTTPS 白名单地址，不能让管理后台直接保存任意 URL。

页面显示/隐藏建议作为页面的独立属性，而不是把 `archived` 当成隐藏开关：

- `DynamicPage`、草稿、修订和 DTO 增加 `hidden`，默认值为 `false`，兼容已有记录；
- 公开页面查询必须同时满足 `status = published AND hidden = false`；
- 后台页面列表仍展示隐藏页面，并明确显示“隐藏”状态，允许编辑、发布、回滚；
- 隐藏页面不能被设为首页，也不能出现在 `bottom_nav`、游戏入口或公开分享配置中；
- 直接访问隐藏路径时，公开接口返回统一的不存在/不可用结果，不泄露页面内容；小程序运行时再回退到当前安全首页或维护页；
- 页面恢复显示后，必须重新发布一个有效 revision，不能只改客户端缓存；
- 页面路径和页面 ID 都按租户隔离，不能通过修改 URL 跨小程序读取。

底部导航、浮动按钮和页面入口均作为 SDUI 块或动作配置下发。客户端只负责渲染和执行白名单动作，后台负责入口顺序、显示/隐藏、目标页面和参数校验。这样首页、游戏中心、游戏详情、游戏兑换码可以复用同一套页面协议，运营只需替换目标配置，不需要重新发布客户端代码。

### 4.5 两个小程序共用一个 SDUI 运行时的协议模型

推荐将客户端职责固定为五层，两个小程序保持相同实现：

```text
请求页面 -> 校验协议 -> 解析数据绑定 -> 渲染 Block -> 执行白名单 Action
```

协议中只允许表达以下内容：

- 页面元数据：`page_id`、路径、标题、分享配置、协议版本、最小客户端版本；
- 布局和组件：`container`、`stack`、`grid`、`list`、`text`、`image`、`game_card`、`redeem_code_card`、`bottom_nav` 等；
- 受控数据源：实体类型、字段白名单、分页参数、租户范围和空态/错误态；
- 受控动作：页面跳转、请求领域端点、复制文本、打开已登记 WebView、登录拦截和刷新页面；
- 条件和能力声明：客户端平台、协议版本、登录状态、页面开关和功能可用性。

协议中禁止出现任意脚本、任意 URL、任意 HTTP 方法、Authorization/Cookie 注入、SQL、内部服务地址和未登记原生能力。客户端必须在协议校验失败时显示安全兜底页，不能执行未知 Block 或 Action。

两端复用关系如下：

| 层次 | 两个小程序是否共用 | 差异来源 |
| --- | --- | --- |
| SDUI 请求、缓存、ETag、协议校验 | 是 | `app_id` 和环境配置 |
| Block 渲染器 | 是 | 页面数据和主题令牌 |
| Action 执行器 | 是 | 服务端动作白名单和微信能力声明 |
| 页面、导航、首页目标 | 不同配置 | 各自租户的 `DynamicPage` 和发布 revision |
| 数据源和领域端点 | 部分共用 | 游戏域、斗艺馆域按租户隔离 |
| 登录/支付/上传/客服能力 | 能力按需启用 | 后端权限、微信审核类目和客户端能力矩阵 |

因此，新增一个页面通常只需要后台新增或复制页面配置、绑定已存在的数据源和动作，再发布 revision。为了达到你的目标，本轮开发不把支付、上传、地图、客服、聊天、订单、物流、售后、斗师接单、WebView、业务类目和资金能力留到以后再设计，而是先完成它们的通用协议、Block、Action、原生适配接口、后端契约和后台能力开关；后续只是在已有能力封套内配置和启用具体业务。

### 4.6 “动态调整”与“无需再次审核”的边界

可以在审核通过后直接动态调整的内容：

- 游戏名称、图标、封面、介绍、标签、排序和上下架状态；
- 首页选择哪个已审核的游戏详情页或兑换码页；
- 底部导航入口的顺序、文案、图标、显示/隐藏和已登记页面跳转；
- 已审核页面内的列表、富文本、图片、空态、公告和运营文案；
- 已登记 HTTPS WebView 地址对应页面内的内容更新，前提是业务域名、类目和实际用途不变；
- 第二个小程序中已经审核范围内的百科、品牌、斗师、商品等页面内容调整。

本轮开发必须预置并完成契约的通用能力包：

| 能力包 | 通用 Block | 通用 Action/原生适配 | 后端契约与后台控制 |
| --- | --- | --- | --- |
| 支付 | `product_card`、`order_summary`、`payment_result`、`price_breakdown` | `create_order`、`pay`、`refresh_order` | 价格快照、订单、支付参数、回调验签、幂等、退款状态、支付开关 |
| 用户上传 | `media_picker`、`upload_progress`、`media_gallery` | `choose_media`、`upload_file`、`delete_media` | 预签名 URL、文件限制、内容安全、归属、删除权限、上传开关 |
| 地图和定位 | `map_card`、`address_card`、`location_picker` | `request_location`、`choose_location`、`open_map` | 地址结构、坐标转换、隐私授权、配送/服务范围、定位开关 |
| 客服 | `contact_card`、`service_entry`、`qr_code` | `open_wechat_service`、`open_external_contact`、`save_qr` | 渠道、来源参数、接待分配、线索状态、客服入口开关 |
| 实时聊天 | `chat_thread`、`message_list`、`message_composer`、`unread_badge` | `send_message`、`upload_chat_media`、`mark_read`、`poll_messages`/`connect_message` | 会话、消息顺序、未读、撤回/屏蔽、轮询或 WebSocket、离线恢复 |
| 订单/物流/售后 | `order_card`、`order_timeline`、`logistics_track`、`after_sale_form`、`evidence_list` | `confirm_order`、`cancel_order`、`apply_after_sale`、`upload_evidence`、`confirm_receipt` | 订单状态机、物流轨迹、售后规则、证据、退款、幂等和售后开关 |
| 斗师接单 | `service_card`、`task_card`、`quote_card`、`schedule_picker` | `accept_task`、`reject_task`、`submit_quote`、`update_service_status` | 斗师身份、权限、排期、报价、收件/回寄、服务审计、结算关联 |
| WebView 域名 | `webview_entry`、`webview_state` | `open_webview` | 按 AppID/租户配置域名白名单、`url_key`、用途、版本和下线状态 |
| 业务类目 | `feature_gate`、`notice`、`compliance_panel` | `check_capability`、`open_policy` | AppID 能力矩阵、类目、隐私协议、审核版本、发布前校验 |
| 会员/广告/提现 | `membership_card`、`ad_slot`、`wallet_card`、`withdraw_form` | `open_membership`、`load_ad`、`request_withdraw`、`refresh_wallet` | 会员权益、广告位、余额账本、提现审核、风控、资金幂等 |

每个能力包都必须完成五个层次：协议定义、Block 注册与渲染、Action 白名单与原生适配、后端端点/错误码/权限契约、后台启用/隐藏/版本校验。能力包可以在首发页面中关闭，但不能只有一个空 Block 或假接口，否则仍然无法做到后续动态启用。

仍然需要重新提交审核或至少进行平台合规确认的变化：

- 从游戏兑换码工具变成商城、支付、社交、直播、内容社区或其他新业务类目；
- 实际启用支付、地图、定位、上传身份证/资质、客服、订阅消息、实时聊天等能力时，必须确认对应 AppID 的类目、隐私协议、资质和域名白名单已经覆盖；能力本身已经预置在客户端，不应再因为缺少运行时 Block 而重新开发。
- WebView 指向新的业务域名、未备案域名或与原审核用途明显不同的站点；
- 新增用户身份、会员、订单、提现、广告或其他需要隐私/资质说明的能力；
- 页面虽然仍由同一协议渲染，但实际业务流程已经超出提交审核时的功能描述。

所以“一个小程序只审核一次”不应作为绝对承诺。准确目标是：**本轮一次性开发完整的通用能力封套；每个 AppID 在首发审核时提交自身会启用的能力范围；审核通过后，页面、入口、业务分支和已覆盖能力通过 SDUI 动态发布。只有新增未纳入能力封套的原生能力或超出 AppID 审核类目的业务，才需要再次升级或审核。**

### 4.7 本轮开发的实际交付边界

本轮不是只交付几个游戏页面，而是交付一套可被两个小程序复用的 SDUI 能力平台：

| 交付层 | 本轮必须完成 | 两个小程序的差异 |
| --- | --- | --- |
| 协议层 | Block/Action Schema、状态模型、数据绑定、能力声明、版本兼容和错误码 | 页面配置、字段绑定和能力开关 |
| 小程序运行时 | 通用渲染器、Action 执行器、微信原生适配、上传/支付/地图/消息/WebView 容器、缓存、降级和安全回退 | AppID、主题、域名和审核能力矩阵 |
| 后端公共层 | 租户、页面、草稿、发布、回滚、页面隐藏、能力矩阵、域名白名单、审计、资源和统一响应 | 每个租户的管理员和发布范围 |
| 游戏领域层 | 游戏、游戏资料、兑换码库存、匿名/会话兑换、复制结果和幂等 | 只在“设身处地游戏”启用 |
| 斗艺馆领域层 | 内容、品牌、斗师、作品、商品、订单、支付、物流、售后、客服、聊天、接单、结算等真实契约 | 只在 dcl/斗艺馆租户启用 |
| 管理后台 | 页面编排、Block 属性编辑、入口显示/隐藏、能力启用、审核状态、WebView `url_key`、发布门禁 | 按 AppID 和租户隔离 |

公共运行时必须有真实的能力注册表，例如：

```text
capability: payment
  blocks: product_card, order_summary, payment_result
  actions: create_order, pay, refresh_order
  native: wx.requestPayment
  backend: /orders, /payments, /refunds
  states: disabled, configured, enabled, blocked, degraded
```

页面发布时，服务端根据 `app_id` 检查：页面使用的 Block、Action、数据源、WebView `url_key`、隐私/类目状态和客户端最低版本是否全部满足。任何一项不满足，页面不能发布到线上。这是“通过一个通用运行时动态调整”的必要门禁。

## 五、数据迁移与接口兼容方案

### 5.1 推荐的数据分层

1. **公共身份层**：第一个小程序不迁移旧用户表、旧 JWT 和旧登录数据；页面不要求登录，兑换动作默认匿名，必要时统一使用 `app_id + wechat_openid` 的 SDUI 用户会话。第二个小程序需要用户态时同样使用 SDUI 会话。H5 身份通过独立身份映射表关联，不把 H5 密码或 OAuth 凭证塞进小程序用户字段。
2. **公共 SDUI 层**：`MiniApp`、`DynamicPage`、草稿、版本、模板、分享和审计。
3. **设身处地游戏业务层**：只包含游戏、游戏来源、游戏介绍、游戏媒体资源、兑换码库存、兑换码匿名领取和必要的运营配置。不存在自动兑换、领取记录、攻略/资讯、游戏工具、关注、互动、UGC、订阅消息和个人中心。
4. **斗艺馆业务层**：合规内容、品牌/百科、斗师、作品、商品、库存、购物车、地址、订单、物流、售后、收藏、客服线索、举报和渠道策略。

### 5.2 第一个小程序的迁移原则

- 游戏、游戏来源、兑换码、游戏介绍和运营配置统一归属目标租户 `app_id = wx7a779add6a689881`；不迁移源用户表，也不为旧用户补造目标用户身份。兑换动作不提供用户可见领取记录，仅保留库存一致性、请求幂等和限流控制所需的最小技术记录。
- 源 `articles`、自动兑换角色/记录、防屏蔽工具配置和用户互动数据不进入目标系统；目标 `articles` 继续保持现有 AI 会员/付费文章语义，避免混用。
- 源 `share_templates` 先通过兼容读取继续服务旧客户端，再将配置转换为 SDUI 页面级 `share_config`；迁移完成前不能删除旧表。
- 新版使用 SDUI 请求层；不移植旧 AES 和旧单 JWT。页面匿名，兑换动作按配置选择匿名或 SDUI 会话；旧线上服务只作为现网版本的临时独立运行环境，不把其认证代码带入统一后端。
- 源游戏来源同步、COS 图片和兑换码库存必须先完成离线迁移与数量校验，再接入新服务；迁移脚本需要可重跑、可审计，不能依赖人工复制。匿名兑换使用受控幂等键与库存事务，不恢复旧登录关系。

### 5.3 兼容接口策略

迁移期间同时存在三类接口：

| 接口层 | 用途 | 生命周期 |
| --- | --- | --- |
| 旧趣兑换码游戏接口 | 仅在旧版客户端仍在线时短期运行 | 新版游戏客户端全量稳定后下线 |
| SDUI 页面接口 | 新客户端读取页面协议和受控数据 | 长期保留 |
| 新领域端点 | 兑换等领域事务动作；第二个项目再扩展订单、互动等能力 | 与领域版本一起演进 |

旧游戏接口和 SDUI 游戏端点在兼容期必须调用同一套游戏领域服务，不能复制两份库存扣减逻辑，否则会产生状态污染和双重扣减。旧用户接口、AES/JWT 和非游戏用户态不做兼容迁移；新客户端不需要迁移旧领取历史。兑换动作是否携带 SDUI 会话只影响限流和归属，不改变页面与数据范围。

## 六、两个客户端的迁移方式

### 6.1 第一个已上线小程序

不能只改后端页面 JSON。必须先发布一个包含以下能力的新版小程序代码包：

- `pages/dynamic/index` 动态承载页；
- 与目标协议一致的块注册表、动作分发器、分享和错误/空态；第一个小程序不接入登录刷新；
- SDUI 配置驱动的底部浮动导航和固定入口，不配置微信原生 `tabBar`；
- 兑换码请求、剪贴板复制和 WebView 等游戏相关微信能力适配；旧用户中心、关注、UGC、订阅消息、自动兑换、兑换记录、防屏蔽工具等不作为新版目标；
- 旧页面路径是否保留，只用于兼容历史分享链接，不代表这些页面继续提供业务功能。

按“运行时一次开发、完整能力预置、后续页面动态发布”的目标，第一个小程序的首次 SDUI 版本应一次性包含通用能力封套：

- 通用布局、文字、图片、富文本、轮播、列表、网格、状态和分享 Block；
- `game_card`、`game_header`、`redeem_code_card` 和 `bottom_nav`；
- 页面跳转、请求兑换码、复制文本、刷新、返回和打开已登记 WebView；
- 一个固定的 WebView 承载页，URL 由后台 `url_key` 映射，不能执行任意外链；
- 协议版本校验、未知 Block 降级、页面缓存、ETag、错误页和安全首页回退；
- 客户端能力清单，例如 `supported_blocks`、`supported_actions`、`protocol_version` 和 `client_version`。
- 支付、上传、地图、定位、客服、聊天、订单、物流、售后、斗师服务、会员、广告、提现等能力的协议类型、渲染器和原生适配接口，即使首发只启用游戏相关页面，也必须能被能力矩阵识别为 `disabled`，而不是客户端完全不认识。

这套能力封套完成并按 AppID 提交后，首页改成某个游戏主页、游戏列表调整、兑换页样式调整、底部入口显示/隐藏以及切换到已登记 WebView，原则上都只需要后台发布 SDUI 页面，不需要重新编译小程序。支付、上传、客服、地图等能力也不需要因为缺少 Block 而重新开发；是否允许上线只由后台能力矩阵、后端真实端点和 AppID 合规状态共同决定。

新客户端上线后，再按页面逐个把旧游戏接口页面切换到 SDUI。建议顺序：

```text
启动页 -> 动态首页 -> 游戏中心 -> 游戏详情 -> 游戏兑换码
-> 匿名请求兑换码 -> 复制到剪贴板
```

每一步都应保留回退开关：页面读取 SDUI 失败、协议版本不兼容或领域端点异常时，回退到已发布安全主页或维护页；旧接口只在兼容期由旧客户端继续使用。

### 6.2 第二个小程序

`dcl` 的 H5 页面不能直接作为微信小程序运行时。建议复用与第一个小程序完全相同的 SDUI 内核，从 H5 组件和设计令牌中提取页面配置、主题和业务数据绑定。两个小程序可以共用代码仓库、协议、Block 和 Action，但仍要针对两个 AppID 分别构建、配置和提交审核。

本地开发中，dcl 使用 AppID `wx8b8e899d4829481a` 注册为独立租户；地图统一使用腾讯地图适配器；客服默认使用微信小程序内置客服组件，小程序内客服作为同一客服能力包的可选实现。斗师认证、接单、结算、售后、会员、广告和提现尚未有最终业务规则，先按《SDUI通用能力平台开发与验收规范》`v1.0.2` 的行业通用状态机生成本地 fixture 和后台可配置参数，业务规则确认后只调整领域配置，不修改页面协议和客户端 Block。

如果目标是让第二个小程序上线后也能长期动态调整，那么首次版本不能只包含当前首页，而应包含本轮抽象完成的完整通用能力封套。页面首发可以只启用合规且近期确定的内容：

- 内容、百科、品牌、斗师、作品和商品的列表/详情；
- 搜索、筛选、图片画廊、简单表单、客服承接和状态页；
- 页面、路径、导航和功能分支的服务端显示/隐藏；
- 登录拦截和 SDUI 会话，但未开放页面不对公开路由返回；
- 已登记的 H5/WebView 入口和统一安全回退；
- 支付、上传、地图、客服、聊天、订单、物流、售后、斗师接单、会员、广告和提现能力的协议与运行时注册项，初始状态按业务开关关闭。

支付、订单、物流、售后、斗师接单、实时聊天、资质上传等能力如果还没有确定业务和审核材料，可以在首发页面中关闭，但不能从协议和运行时中删除。等真实领域服务和平台资质成熟后，应直接启用已有能力包，而不是重新设计一套客户端页面协议。

原来的业务分阶段仍然成立：

1. 第一批只上线合规内容、百科、品牌馆、斗师列表/详情、作品详情、客服承接。
2. 第二批接入商品、收藏、库存和服务预约。
3. 第三批接入购物车、地址、订单、支付、物流和售后。
4. 最后接入斗师端工作台、结算、举报和运营闭环。

不要把 H5 的 204 个路由一比一变成 204 个小程序页面。小程序应按用户任务和页面族收敛路由，页面细节由 SDUI 配置；复杂状态机仍由后端领域服务和少量通用客户端交互承载。

### 6.3 dcl H5 的后续接入

H5 可以继续保留现有 React 路由和视觉实现，但需要：

- 将 `H5MockApiClient` 替换为真实 HTTP 数据客户端；
- 接入 H5 独立登录和会话刷新；
- 使用后端渠道/地区/年龄策略过滤内容和商品；
- 明确 H5 与小程序哪些资产可互通、哪些必须隔离；
- 增加 CORS、CSRF、支付回调、文件上传和 SEO 服务端要求。

H5 的 UI 验收通过不等于业务可上线，当前审计记录已经明确这一点。

## 八、上线与微信平台约束

“服务端驱动”不等于绕过微信审核。必须先审核发布包含新运行时和原生能力的代码包，之后页面文案、图片、排序和已登记动作才能由后台动态更新。首页切换到游戏主页或 WebView 只能使用已审核类目、已备案的 HTTPS 业务域名和已登记能力；如果实际业务形态发生变化，仍需按微信规则重新提交审核，不能把动态配置当成规避审核的通道。

上线前至少要准备：

- 两个小程序分别配置 request、downloadFile、uploadFile 和业务域名白名单；
- COS/CDN 使用有效 HTTPS 证书，并验证微信真机可读；当前文档记录过 `minicdn.a0free.com` 的本机证书过期提示，需重新核对生产边缘证书；
- H5 业务域名、WebView 域名和服务端域名白名单；
- 每个小程序独立的微信登录配置；
- 商品支付商户号、API v3 Key、证书、私钥和 AppID 绑定；
- 微信隐私协议、用户授权、内容安全、客服、订阅消息和类目审核；
- 旧版本和新版本同时访问时的数据库兼容与回滚方案。

## 九、主要风险

### 高风险

- 直接把两个项目的 `users`、`articles` 或管理员表合并，导致数据串租户或语义冲突；
- 先切换页面协议、后补领域事务，出现页面能看但兑换/订单/售后不可用；
- 把旧 AES/JWT 认证代码混入新版游戏链路，造成两套会话规则和状态污染；
- 把 `request_data` 当成任意 HTTP 代理，造成内网访问、凭证泄漏或微信审核风险；
- 只在前端隐藏敏感内容，后端搜索、推荐、分享或通知仍然返回受限数据。

### 中风险

- 页面/动作能力未覆盖真实微信基础库；
- CDN、WebView、图片和上传域名未加入白名单或证书异常；
- H5 Mock 状态与真实订单/售后状态不一致；
- 没有记录页面 revision、领域版本和回滚证据，出现问题无法定位。

## 十三、SDUI 页面完成度与 Block 缺口

### 13.1 先给结论

当前 SDUI 已经足够完成“内容展示型”和“简单操作型”页面，但还不足以完整承载 dcl 中所有 204 条用户端/斗师端路由。你的目标不是把这些能力推迟到以后，而是在本轮开发中把它们抽象为可复用的能力包；业务是否启用由后台配置和后端真实状态决定。原因不是页面数量，而是以下三类能力边界：

1. **已有块可组合完成**：首页、列表、详情、资讯、百科、游戏资料、游戏兑换码展示、时间线、空态/错误态、简单查询和 WebView 跳转。
2. **已有块能画出来但交互不完整**：复杂表单、图片上传、评论图片、商品 SKU、筛选、地址、预约、订单、评价和个人资料。
3. **当前缺少运行时能力或领域协议**：购物车/订单状态机、物流、售后纠纷、斗师接单、结算、聊天、OCR、原生地图、客服和持久化通知；这些能力已列入本轮通用能力包，必须完成后才能宣称第二个小程序具备可启用的完整运行时。

因此，不能用“所有页面都能返回一份 `BlockItem[]`”作为完成标准。正确标准应是：页面视觉可渲染、主任务可完成、状态可持久化、失败可恢复、动作有真实后端端点。

### 13.2 当前已注册但实现深度不足的块

当前后端白名单登记了约 48 个 block，但以下类型在前端 `BlockRenderer` 中实际落到 `GenericBlock`，属于“协议可接受、语义组件未专门实现”：

| Block | 当前实际能力 | 主要问题 |
| --- | --- | --- |
| `game_header` | 通用标题/图片/正文卡 | 没有游戏图标、封面、标签、版本、厂商、截图和主操作的稳定布局 |
| `result_table` | 通用 rows/items 列表 | 没有表头、列类型、横向滚动、空值和结果复制语义 |
| `contact_card` | 通用卡片 | 没有微信客服按钮、企业微信、二维码保存或来源参数 |
| `map_card` | 通用卡片 | 没有地图原生组件、位置授权、导航和地址选择 |
| `event_card` | 通用卡片 | 没有预约状态、活动时间、库存/名额和订阅动作布局 |
| `poll` | 通用 options 列表 | 没有单选/多选、提交态、投票结果和重复提交控制 |
| `feed_list` | 通用列表 | 没有统一分页、加载更多、点赞/收藏/评论统计和局部状态 |
| `custom` / `custom_block` | 通用图文卡片 | 可以快速做视觉原型，但不应承载订单、支付、上传和复杂表单 |

这意味着“注册了 block”不等于“该页面业务已经完成”。`GenericBlock` 适合兜底和轻量内容，不适合替代领域交互组件。

### 13.3 第一个小程序：设身处地游戏兑换码页面

第一个小程序最终收敛为四类页面，不保留自动兑换、兑换记录、防屏蔽工具、UGC、关注、个人中心和原生 TabBar：

| 页面/功能 | 现有 SDUI 完成度 | 说明 |
| --- | --- | --- |
| 动态首页 | 高 | 页面完全由 SDUI 发布版本决定；可展示游戏入口，也可切成 H5 WebView 入口或某个游戏主页 |
| 游戏中心 | 高 | `list`/`grid` + `game_card` 可组合；无需旧字母索引和复杂筛选时不必新增列表组件 |
| 游戏详情 | 中高 | 可用 `game_header`、`item_grid`、`rich_text`；当前 `game_header` 只是通用卡，需要专用实现 |
| 兑换码展示 | 高 | `redeem_code_card`/`coupon_card` 可用；公开协议必须只返回脱敏码，明文通过受控动作按需取得 |
| 兑换码请求/复制 | 中高 | `request_data` + 受控游戏兑换码端点 + `copy_text` 可完成；匿名请求，不提供用户可见领取历史，不需要登录 |
| 底部导航 | 当前缺失 | 不能使用原生 `tabBar`；需要 SDUI `bottom_nav`/`floating_nav` 固定在安全区，并按后台配置显示/隐藏入口 |
| H5 游戏入口 | 中高 | `open_webview` 动作已存在；目标必须是已部署并加入微信业务域名白名单的 HTTPS 地址，`codex://threads/...` 不能直接使用 |

第一个小程序的最小新增清单只有：

- `game_header` 专用实现；
- `bottom_nav`/`floating_nav` 固定底部导航；
- 完善 `game_card` 和 `redeem_code_card` 的字段/动作；
- 一个只返回目标游戏兑换码的受控端点；首发允许匿名调用，服务端负责库存扣减、幂等和限流，不返回其他用户或库存敏感信息；后续可切换为 SDUI 会话而不改页面协议；
- 首页目标配置必须同时保存目标类型、`page_id`/`url_key` 和游戏参数，不能只保存 `current_page` 字符串；
- 如果要求进入首页后自动打开 H5，需要页面级 `on_load` 动作；如果允许用户点击后进入，则直接复用 `open_webview`。

### 13.4 dcl 用户端页面族

以下按页面族判断，不建议把 149 条路由逐页做成独立组件。

| 页面族 | 代表页面 | 判断 | 主要缺口 |
| --- | --- | --- | --- |
| 通用状态 | 登录、网络失败、空态、加载、下架、支付异常 | 大部分可完成 | 登录弹窗、确认弹窗、底部弹层目前没有通用 overlay block |
| 首页/内容 | 首页、搜索、文章详情、动态详情、评论、举报、分享 | 内容展示可完成，互动不完整 | 搜索建议、评论图片、举报表单、分享海报预览、用户卡片 |
| 百科 | 品牌馆、品牌故事、器型材质、知识详情 | 高 | 资料筛选、来源折叠、收藏状态可用组合表达，但缺少稳定的筛选和收藏反馈组件 |

### 13.6 本轮必须内置的通用 Block 与能力集合

不建议为 204 条路由创建 204 个专用 Block。应按真实交互语义建立可跨小程序复用的能力包。下面是本轮开发的运行时基线，不是“以后再做”的待办清单：

| 优先级 | 建议 Block/能力 | 覆盖页面 |
| --- | --- | --- |
| P0 | `form` v2：多字段、校验、默认值、提交状态 | 登录、查询、估价、入驻、资料、售后、客服、提现 |
| P0 | `media_picker`、`upload_progress`、`media_gallery` | 用户上传、OCR、作品、二手、资质、聊天媒体、售后证据 |
| P0 | `overlay`：`dialog`、`action_sheet`、`bottom_sheet`、二次确认 | 登录、SKU、地址、支付、退款、注销、不可逆确认 |
| P0 | `bottom_nav`、`floating_action`、`feature_gate` | 两个小程序的导航、浮动入口、页面/能力显示隐藏 |
| P0 | `sku_selector`、`quantity_stepper`、`price_breakdown` | 商品详情、购物车、订单确认、支付 |
| P0 | `order_card`、`order_summary`、`order_timeline`、`payment_result` | 商品订单、服务订单、支付结果、确认收货 |
| P0 | `logistics_track`、`after_sale_form`、`evidence_list` | 物流、退款、售后、纠纷、证据提交 |
| P0 | `map_card`、`address_card`、`location_picker` | 地图、定位、地址簿、配送和服务范围 |
| P0 | `contact_card`、`service_entry`、`qr_code` | 客服、企业微信、二维码、线索承接 |
| P0 | `chat_thread`、`message_list`、`message_composer`、`unread_badge` | 实时聊天、离线留言、斗师/客服会话 |
| P0 | `service_card`、`task_card`、`quote_card`、`schedule_picker` | 斗师接单、报价、预约、服务进度 |

下列能力虽然需要原生或平台适配，但也必须在本轮作为统一 Action 接口和客户端能力注册项内置，不能让业务页面自行调用微信 API：

- `upload_file`/`upload_image`：统一处理微信选择文件、COS 预签名、进度、失败重试和内容审核；
- `location`/`map`：统一处理位置授权、地图 SDK、地址结构和导航；
- `ocr`：统一处理图片上传、OCR 服务端点、结果确认和手动修正；
- `wechat_customer_service`：统一处理微信原生客服能力、来源参数和降级二维码；
- `realtime_message`：统一处理轮询/WebSocket、未读数、消息顺序和离线恢复；
- `wechat_pay`/`wallet`/`withdraw`：统一处理支付调起、余额展示、提现提交和结果刷新；
- `open_webview`：统一处理域名白名单、`url_key`、来源参数、加载失败和安全回退；
- `transform_text`：只能执行受控、可审计的固定转换，不能开放任意脚本。

### 13.7 不能靠新增 Block 单独解决的问题

即使补齐上述 Block，以下事项仍然必须由本轮能力包的后端领域层和运营控制层完成：

- 游戏兑换库存扣减、匿名领取幂等和防超发；
- 商品库存、购物车价格快照、订单状态机、支付回调和退款；
- 服务预约排期、报价确认、收件/回寄、售后和纠纷裁定；
- 斗师认证、角色权限、接单任务、结算和提现；
- 内容审核、图片审核、敏感词过滤、渠道/地区策略；
- H5 与小程序的身份、资产和订单隔离/映射；
- 分页、缓存、审计、通知、搜索索引和报表。

换句话说，Block 解决“客户端如何稳定展示和触发动作”，领域服务解决“动作是否允许、如何落库、如何幂等、失败如何恢复”。两者不能互相替代。

### 13.8 推荐实现顺序

如果目标是先让第一个游戏小程序上线，建议只做以下闭环：

```text
bottom_nav -> game_header -> game list/detail
-> redeem_code_card -> game.redeem -> copy_text
-> homepage_target -> game detail / game redeem / approved HTTPS WebView
```

运行时基础阶段必须同时完成上述能力包的协议、Block、Action、客户端适配接口、后端契约和后台开关；业务上线仍按领域成熟度分阶段启用：

```text
内容/百科 -> 斗师/作品只读 -> 客服承接
-> 商品/收藏/预约 -> SKU/购物车/订单/支付
-> 物流/售后/纠纷 -> 斗师接单/作品审核/结算
```

这样可以把“SDUI block 缺口”和“业务后端缺口”分开验收，避免页面已经能显示，却被误判为整条业务链路已经完成。
